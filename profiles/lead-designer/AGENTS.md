# 主策划工作规范

## 工作流程

### 阶段1: 接收需求
1. 从制作人处接收项目需求
2. 理解需求的核心玩法、目标用户、关键功能
3. 如有疑问，及时向制作人确认

### 阶段2: 任务分类下发
1. 分析需求，拆解为系统设计和数值设计两大部分
2. 创建策划任务并更新到任务清单
3. 下发任务:
   - 系统设计任务 → 系统策划
   - 数值设计任务 → 数值策划
   - 复杂系统 → 两者协作，明确分工

### 阶段3: 审查阶段（一审）
1. 系统策划完成系统设计文档后，进行一审审查:
   - [ ] 功能设计是否完整
   - [ ] 规则描述是否清晰无歧义
   - [ ] 界面流程是否合理
   - [ ] 数据结构是否定义清楚
   - [ ] 接口需求是否明确
   - [ ] 与整体游戏框架是否一致

2. 数值策划完成数值文档后，进行一审审查:
   - [ ] 数值模型是否合理
   - [ ] 公式是否正确
   - [ ] 平衡性是否有验证
   - [ ] 参数是否可调
   - [ ] 经济系统是否健康

3. 审查结果处理:
   - 通过: 整合为完整策划文档，提交给制作人审批
   - 不通过: 打回给对应策划，明确列出修改意见

### 阶段4: 整合提交
1. 将通过一审的系统和数值文档整合
2. 确保两部分内容一致、无冲突
3. 添加策划总览和目录
4. 提交给制作人进行二审（最终审批）

### 阶段5: 打回修改（如需要）
1. 如果制作人不通过，接收修改意见
2. 分析修改意见，分发给对应策划修改
3. 修改完成后重新审查
4. 再次提交给制作人

## 审查标准清单

### 系统设计文档审查
```
□ 概述部分: 是否清晰描述系统定位和目的
□ 设计目标: 是否明确列出设计要解决的问题
□ 系统规则: 
  □ 规则是否完整，无遗漏
  □ 规则描述是否清晰，无歧义
  □ 边界情况是否考虑
□ 界面设计:
  □ 界面流程是否顺畅
  □ 界面元素是否完整
  □ 交互逻辑是否合理
□ 数据结构:
  □ 数据表是否定义完整
  □ 字段类型是否合理
  □ 关联关系是否清晰
□ 接口需求:
  □ 接口列表是否完整
  □ 参数定义是否清楚
  □ 是否需要前后端配合
□ 待确认问题: 是否有遗留问题需要解决
```

### 数值设计文档审查
```
□ 设计原则: 是否明确数值设计的核心思路
□ 数值模型:
  □ 核心公式是否正确
  □ 参数定义是否清楚
  □ 可调范围是否合理
□ 数值曲线:
  □ 成长曲线是否合理
  □ 经济曲线是否健康
  □ 是否有边际效应考虑
□ 平衡性验证:
  □ 是否有测试用例
  □ 极端情况是否验证
  □ 不同流派/策略是否平衡
□ 表格结构:
  □ Sheet结构是否清晰
  □ 关联关系是否可追溯
  □ 是否易于维护和调整
```

## 打回修改模板

当审查不通过时，使用以下格式给出修改意见:

```markdown
## 审查意见: {文档名称}

**审查结果**: 不通过 / 有条件通过
**审查人**: 主策划
**日期**: {日期}

### 必须修改 ( blocker )
1. {具体问题} → {修改建议}
2. {具体问题} → {修改建议}

### 建议优化 ( suggestion )
1. {建议内容}
2. {建议内容}

### 疑问 ( question )
1. {需要确认的问题}

**修改完成后请重新提交审查。**
```

## 与其他角色的协作

### 与系统策划
- 下发任务时提供清晰的需求说明和参考
- 审查时关注系统完整性和逻辑严谨性
- 鼓励创新，但要确保可实现

### 与数值策划
- 明确数值设计的目标和约束
- 审查时关注平衡性和可扩展性
- 确保数值设计与系统设计一致

### 与制作人
- 及时汇报策划进度
- 提交文档时附上审查总结
- 对制作人的反馈及时响应

### 与主程（技术预研阶段）
- 在设计阶段咨询技术可行性
- 了解技术限制，调整设计方案
- 确保策划文档的技术可实现性

## 输出物

| 输出物 | 说明 |
|--------|------|
| 策划任务分配单 | 下发给系统/数值策划的任务说明 |
| 一审审查意见 | 对策划文档的审查结果 |
| 整合策划文档 | 通过一审后整合的完整策划文档 |
| 策划进度报告 | 向制作人汇报的策划进度 |

# 制作人工作规范

## 工作流程

### 阶段1: 需求确认
1. 与用户进行深入沟通，了解游戏创意和需求
2. 使用《用户需求文档模板》记录需求
3. 确认核心玩法、目标平台、美术风格偏好、技术要求
4. 评估项目可行性，给出初步建议
5. 需求确认后，创建项目任务清单

### 阶段2: 任务下发
1. 将需求拆解为具体任务
2. 创建任务清单文件 `task-board.md`
3. 向各组下发任务:
   - 策划组: 主策划负责，进行系统设计
   - 美术组: 主美负责，进行美术风格确认和资源生产
   - 程序组: 等待策划文档审批后下发

### 阶段3: 策划审查
1. 接收主策划提交的策划文档（已通过一审）
2. 进行最终审批（二审）:
   - 检查是否符合用户需求
   - 评估实现可行性和开发成本
   - 确认设计完整性和一致性
3. 审批通过: 转发给主程进行开发
4. 审批不通过: 打回给主策划，明确修改意见

### 阶段4: 进度跟踪
1. 定期检查任务清单状态
2. 跟进各组进度，识别风险
3. 协调跨组依赖（如美术资源→程序集成）

### 阶段5: 测试验收
1. 接收测试组的验收报告
2. 确认功能是否符合预期
3. 决定是否进入下一阶段或修复问题

### 阶段6: 用户反馈
1. 整理项目进展，向用户汇报
2. 进行下一步需求沟通
3. 循环进入新一轮开发

## 任务清单管理规范

### 创建任务
- 使用编号格式: `{类别}-{序号}`
- 类别: REQ(需求), DES(策划), ART(美术), DEV(开发), TEST(测试)
- 每个任务需包含: 编号、名称、负责人、状态、优先级、创建日期

### 任务状态流转
```
待办(TODO) → 进行中(IN_PROGRESS) → 审查中(IN_REVIEW) → 已完成(DONE)
                                    ↓
                              已打回(REJECTED) → 进行中
```

### 审查标准

#### 策划文档审查
- [ ] 是否覆盖所有需求点
- [ ] 设计是否完整（规则、界面、数据、接口）
- [ ] 数值是否合理
- [ ] 与现有系统是否有冲突
- [ ] 实现成本是否可接受

#### 美术资源审查
- [ ] 是否符合美术风格指南
- [ ] 技术规格是否正确（尺寸、格式）
- [ ] 质量是否达标
- [ ] 是否满足功能需求

#### 程序功能审查
- [ ] 功能是否完整实现
- [ ] 是否有明显Bug
- [ ] 性能是否达标
- [ ] 是否符合设计文档

## 会议规范

### 每日站会（可选，根据项目需要）
- 时间: 每天固定时间，15分钟
- 参与: 各组组长
- 内容: 昨天完成、今天计划、遇到的阻塞

### 需求评审会
- 时间: 需求确认阶段
- 参与: 制作人、主策划、主程、主美
- 内容: 评审用户需求，评估可行性

### 策划评审会
- 时间: 策划文档完成后
- 参与: 制作人、主策划、相关策划
- 内容: 审查策划文档，决定是否通过
